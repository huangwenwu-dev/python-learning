# 第15周 D1 笔记：最小 StateGraph（2026-10-09）

环境：langgraph 1.2.9。今天全程不调大模型，节点就是普通 Python 函数。

## 一、五个词

| 词 | 我的原话 | 补全后的一句 |
|---|---|---|
| State | 整张单子 | 流转单：一个字典，有哪几栏由 TypedDict 声明，所有节点读写的是同一张 |
| Node | 一个工位 | 工位：本质是一个函数，收到整张单子，只交回自己负责的那一栏 |
| Edge | 工位之间 | 工位之间"下一站交给谁"的规定 |
| compile() | 流程图 | 开工前检查流程图有没有接错线（比如有没有入口），通过后得到能跑的 graph |
| invoke() | 执行 | 真的投一张单子进去跑一遍，返回最后的整张单子 |

注意：画流程图的是 `add_node` / `add_edge`，`compile()` 是检查这张图，不是画图。

## 二、今天最核心的一句

**节点只交回自己那一栏，框架把这一栏合到单子上，其他栏保留原样。**

- 节点：只管交回自己改的栏
- 框架：替我调用节点、把单子递进去、把交回的栏合上去
- State：被读、被写的那张单子
- builder 是流程图（只有工位和箭头），state 是流转单（上面才有值）

读和写怎么分：

- `state['某栏']` 是读单子
- `return {"某栏": ...}` 是写，交回一栏

最终输出 `{'city': '成都', 'weather': '雨', 'plan': '成都今天雨,不适合散步'}` 里每个字段的来历：

| 字段 | 谁写的 | 哪一行 |
|---|---|---|
| city | 进门时自带，不是节点写的 | 第25行 `invoke({"city": "成都"})` |
| weather | 节点 check_weather | 第11行 `return {"weather": "雨"}` |
| plan | 节点 make_plan（先读了 city 和 weather） | 第15行 `return {"plan": ...}` |

没填的栏是"压根不在"，不是"在但空着"：A 收到的单子里只有 city 一个 key。

## 三、TypedDict 和 Pydantic

我的比喻：**一个像不检查的登记表，一个像会拦人的门卫。**

- TypedDict：只印栏目，运行时不检查。`{"city": 123}` 类型错、漏栏都照跑。
- Pydantic：运行时校验，同样的内容报 `ValidationError`，两个问题一次都报。
- 造实例的写法不同：TypedDict 用花括号 `{"city": 123}`，Pydantic 用 `类名(city=123)`。
- 分工：对外的安检口用 Pydantic，内部流转的单子用 TypedDict。

## 五、三个破坏实验

| 实验 | 冒在哪行 | 报错类名 | 说明了什么 |
|---|---|---|---|
| 删掉 `add_edge(START, ...)` | 第24行 compile() | ValueError | compile 会查图的结构，订单进门前就拦下 |
| `check_weather` 写成 `check_weather()` | 第18行 add_node | TypeError | 加括号是当场调用，还没轮到框架就出错 |
| 栏名拼成 `"wether"` | 第15行（B 里） | KeyError | 框架不拦错栏；病根在上游 A，症状在下游 B |

读 traceback 的方法：从上往下是"谁调用了谁"。最上面是我自己的文件，告诉我是哪一行触发的；最下面是真正抛错的地方。找自己的错往上翻。

## 六、两个视角

| | invoke | stream(stream_mode="updates") |
|---|---|---|
| 给我什么 | 最后整张单子 | 每个工位各自交了什么 |
| 打印几次 | 1次 | 每个节点1次 |

两者都是"投单子"的方式，各自都要在括号里递一张初始单子。updates 里看不到 city，因为它不是任何工位交回的。
