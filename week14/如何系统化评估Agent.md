# 如何系统化评估一个 Agent

## 一、为什么需要评估体系

- **没有它会怎样**：Agent 是多步链路（检索 → 拼提示 → 模型 → 工具），最后答案错了，根本不知道是哪一步出的问题。只能靠 print、靠猜、靠反复试，改完也说不清到底有没有变好。
- **一句话**：先有尺子，才能量长短。

## 二、第一步：建立尺子（评测集）

- **从哪来**：
  - 手写核心用例：业务上最常被问、最不能答错的问题
  - 从真实 trace 捞：线上用户反馈答错的、评测里判 0 分的、trace 形状异常的（轮数特别多、工具报错的）
- ⭐ **结构要求**：一半典型题 + 一半"会出错的题"
  - 必须覆盖：资料里没有的（防幻觉）、跨文档、多轮带指代、需要综合推理
- **参考答案怎么写**：写出关键事实（关键词、数字、结论），能作为判断依据；不追求一字不差
- ⚠️ **判断评测集好坏的标准**：能不能测出系统的弱点。全是送分题，跑出 95% 也没有意义——满分只说明题太简单，不说明 Agent 好。
- **修好的题怎么办**：线上反馈里答错的题，修好之后加进评测集变成常驻用例（回归测试：每次改完都把老题重跑一遍，确保以前修好的没有退回去）

## 三、第二步：让评判自动化（evaluator）

| 评判器 | 适合 | 优缺点 |
|---|---|---|
| 代码规则式（code_rule） | 有固定关键词/数字的题；"资料里没有"的防幻觉题（查有没有出现禁止词、有没有说"未找到"） | 快、免费、结果稳定；措辞一变就可能误杀 |
| LLM-as-judge（LLM 裁判） | 需要语义理解的题：综合推理、跨文档 | 能理解意思相同但说法不同；花钱，而且裁判自己也会判错 |
| 人工 | 裁判本身不可靠、或者需要业务判断的题 | 最准；最慢，没法每次都做 |

- **选型逻辑**：确定性的用规则，语义的用 LLM 裁判，拿不准的交给人工
- ⚠️ **必须做的一件事：裁判校准**。裁判本身也会错——LLM 裁判可能把对的判错、错的判对，code_rule 可能因为措辞不同误杀。
  - 具体做法：抽一批题人工判一遍，和裁判的结果逐条对比；一致率低就先改裁判（改规则 / 改裁判提示），再信它的分数
  - 不抽查，就不知道报告里的分数是 Agent 的真实水平，还是被裁判污染了

## 四、第三步：出问题时怎么定位（trace）

- **trace 结构**：trace 是一棵树（一次完整运行），run 是树上的节点（一步：一次检索、一次模型调用、一次工具调用）
- ⭐ **定位思路**：沿 trace 树逐层缩小范围，找第一个"**输入对、输出错**"的节点——只有这个 run 的输入是正确的、输出却是错的，才能判定问题出在它这里；输入就已经错了，是上游的锅
- **四类故障速查表**：

| 故障 | 症状 | trace 里怎么看 | 该改哪里 |
|---|---|---|---|
| 检索没召回 | 答不上来，或者答非所问 | 看检索 run 返回的 documents，里面没有答案 | 切块大小、Top-K、embedding / 语义漂移、元数据过滤 |
| 提示有问题 | 资料明明在，模型没用上或用错 | 检索结果里有答案 → 看 model run 的输入（提示怎么拼的）和输出对比 | 提示词：约束太紧/太松、资料的位置和顺序 |
| 工具调错 | 工具报错、参数不对、调了不该调的工具 | 看 tool run 的 input（参数）和 output（返回/报错） | 工具的 docstring、args_schema、错误返回说明 |
| 编排 bug | 死循环、漏步骤、顺序错、该停不停 | 不看单个节点，看**树的形状**：节点数量、顺序、有没有重复打转 | 流程逻辑、停止条件、最大轮数 |

- **关于幻觉**：幻觉（模型编出资料里没有的内容）是**症状**，不是独立的原因。背后通常是：检索没召回（没资料可用，模型只好自己编）或提示有问题（没约束"资料里没有就说不知道"）。在 trace 里看法：输出里有没有检索结果中不存在的内容，然后再按上面两类去查。
- ⭐ **最关键的二分法**：看检索 run 里有没有相关资料
  - 没有 → 检索没召回
  - 有，但模型没用 → 提示有问题

## 五、第四步：验证改动（experiment 对比）

- **experiment 是什么**：一次完整评测运行的记录——某个版本的 Agent 在某个 dataset 上跑出的全部结果。改了 Agent 就跑一个新 experiment，和旧的并排比较。
- **实验铁律**：控制变量，一次只改一个变量，其余全部保持不变。否则分数的差异归因不到任何一处改动上。
- **看什么**：准确率 + token 成本 + ⭐ 逐题对比（不只看总分：哪些题从错变对，有没有题从对变错）
- ⚠️ **别被数字骗**：
  - 小样本下的差异可能只是噪音（同一题跑两次答案都可能不同）
  - 便宜 ≠ 划算：token 省了，准确率掉了，不一定值
- **成本要心里有数**：
  - RAG 烧钱的大头是**输入** token：每轮都要把 system prompt + 检索结果 + 历史对话全部重新提交
  - 多轮工具调用是滚雪球：每多一轮，历史里就多一条 ToolMessage（通常很长），下一轮要重新提交全部历史，每次都比上一轮更大

## 六、完整闭环（⭐ 一张图）

```
        ┌───────────────────────────────────────────┐
        ↓                                           │
① 发现问题    ← 评测集跑出低分 / 线上反馈答错           │
        ↓                                           │
② 看 trace 定位 ← 找第一个"输入对、输出错"的 run        │
        ↓        检索 / 提示 / 工具 / 编排？           │
③ 针对性地改   ← 只改定位到的那一处，一次一个变量        │
        ↓                                           │
④ 重跑评测验证 ← 新 experiment 和旧的逐题对比          │
        ↓                                           │
   涨了 → 保留；答错的题留在评测集作回归用例             │
   没涨 → 先撤回这次改动，回 ② 重新定位 ─────────────────┘
```

**一个 bad case 的完整处理流程**：
1. 从评测报告里找到它（例如 LangSmith experiment 里 llm_judge 判 0 分的那几行），或来自线上反馈
2. 找到这道题对应的 trace
3. 看检索结果里有没有正确答案 → 区分"检索没召回"还是"提示有问题"（工具、编排类问题看 tool run 和树的形状）
4. 检索没召回 → 看返回的 documents，是切块问题、Top-K 问题还是语义漂移
5. 检索有答案但没用上 → 看 model run 的输入（提示词怎么写的）和输出，是约束太紧还是模型没读全
6. 只改定位到的那一处
7. 重跑评测，和原分数逐题对比
8. 没涨：撤回改动，重新定位，不换方向乱改；涨了：保留，这道题作为常驻用例留在评测集里

## 七、我的实战记录

### 用这套流程定位的一道题：id=10

- **① 发现**：框架版 experiment 里 llm_judge 判 0 分。问题"AI Agent 在工业制造领域有哪些落地案例？"，参考答案有两个案例（首钢热轧线审核 1 小时→秒级；具身智能机器人采购额同比增长 2.3 倍），Agent 只答出首钢，并说"资料中仅找到一个"。先核对裁判理由，确认裁判没有判错。
- **② 定位**：
  - 两次检索召回的块分别是 3/5/4 和 5/0/1，**chunk_2 一次都没被捞到**
  - 在原文里搜"2.3"，案例正好落在 chunk_2
  - 检索 run：输入的问题是对的，输出里没有案例 → **输入对、输出错** → 故障类型：**检索没召回**
  - model run：拿到的资料里本来就只有一个案例，回答"仅找到一个"是诚实的，这一步不背锅
- **病根（两层）**：
  1. 按字数硬切，不认章节、没有语义边界——"三、具身智能与终端革命"这个标题落在 chunk_1 末尾，正文和案例被切进了 chunk_2
  2. 一块里塞了多个章节的话题，向量被稀释成"什么都沾一点、什么都不突出"——chunk_2 里明明有"工业企业"，依然排不进 Top-3（就是第 11 周记下的"万能块现象"）
- **③ 改法选择**：选**按章节/段落边界切（语义切块）**。不选"调大 Top-K"——那是花钱买概率，C 是不多花钱把病根修了。
- **④ 验证计划**（待做）：重建索引后重跑 10 题，逐题对比，盯两件事——id=10 有没有修好、其余 9 题有没有从对变错。
- **状态**：已定位、已确定改法，**尚未实施**，分数变化待下次补。

### 其他发现

- **评测集本身的问题**：id=5 手写版在无记忆的情况下也答对了，说明这道题测不出记忆能力，这一分含水分
- **题号对不上的坑**：LangSmith 表格左边是行号，不是自己的题号，今天因此点错过一次题。以后建评测集时要把自己的题号写进 metadata（如 `{"qid": 10}`）

### 手写 vs 框架

- **手写适合**：流程固定、知识库小（十几块）、不需要多轮记忆、追求低延迟（0.65s vs 2.04s）。比如内部小工具、一次性问答脚本
- **框架适合**：需要多轮记忆、需要模型自主决策（该不该检索、检哪份文档）、需要可观测性和成本核算、知识库会持续增长

### 当前水平与短板

- 框架版 llm_judge 0.90（9/10），但这个数偏乐观：id=5 测不出记忆能力，这一分含水分；id=10 已定位为切块问题（见上）。扣掉存疑的题后，真实区分能力低于 0.90，具体多少这套评测集给不出答案
- **下一步优先改**：① 实施语义切块并重跑验证 id=10 ② 补一道真正需要记忆才能答对的题，替换 id=5
