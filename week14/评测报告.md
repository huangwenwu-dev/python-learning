## 一、评测设置

**评测集** 10 条：典型 4（id 2/3/4/10）、资料里没有的 2（id 1/9）、综合推理 2（id 7/8）、跨文档 1（id 6）、多轮带指代 1（id 5）。知识库两份文档：员工手册、AI Agent 未来发展趋势。

**判卷器**
- `code_rule`：只判 id 1/4/9，正则与关键词查特定内容是否出现。
- `llm_judge`：deepseek-chat，temperature=0。两项任一不满足即 0——语义与参考答案一致；出现的数字必须与参考答案逐一核对。

**对比版本**
- **A 手写版**（`week14/hand_rag.py`）：纯 Python + NumPy，JSON 存向量，手算余弦，固定流程每次必检索，无记忆。
- **B 框架版**（`week14/frame_agent.py`）：LangChain 1.x + Chroma + SqliteSaver + SummarizationMiddleware，模型自主决定是否检索。

**变量控制**

| 参数 | 统一成 | 备注 |
|---|---|---|
| 分块 / embedding | 500-50 / text-embedding-v3 | 统一 |
| Top-K | 3 | 统一。改前误记框架版为 4，实为 `search` 默认 3 |
| 生成模型 | deepseek-v4-flash | 统一。框架版原用已弃用别名 `deepseek-chat` |
| temperature | 0 | 统一。框架版原未设置 |
| 思考模式 | 关闭 | 统一。两版显式传 `thinking: disabled`。**关闭前手写版 `temperature=0` 并不生效**——思考模式不支持该参数 |
| 拒答句 | "资料中未找到相关信息" | 统一，与 code_rule 关键词对齐 |
| 知识库 | 两份文档 | 统一。手写版重建索引 `w14_index.json` |
| 记忆 / 工具自主 / 存储 | — | **故意保留**，这三项正是两种范式的本质差异 |

**已知问题**
1. `frame_tools.py` 仍依赖 `week13/retriever_test.py`，Chroma 库仍读 `week13/chroma_db`。
2. 两版索引来源不同（JSON vs Chroma），分块参数一致但不是同一份向量。
3. 手写版无 token 数据，原因见第二节。

## 二、总体结果

| | code_rule | llm_judge | P50 | P99 | 总 token | 每题均值 |
|---|---|---|---|---|---|---|
| A 手写版 | 1.00 | **0.50** | 0.65s | 0.94s | 无数据 | — |
| B 框架版 | 1.00 | **0.90** | 2.04s | 2.81s | 25.78K | ≈2578 |

- **手写版 token 缺失**：它用 OpenAI SDK 裸调，未向 LangSmith 上报 usage；框架版走 `ChatDeepSeek` 自动上报。这是"框架替我做了什么"的一项——可观测性接线。成本维度改用延迟替代。
- **手写版快约 3 倍**：固定流程一次生成 vs 先判断调不调工具再生成。
- **code_rule 满分参考价值有限**：它只查关键词，不核完整性。id=4 上出现过 code_rule 判 1、llm_judge 判 0 的分歧。

## 四、失败案例分析

手写版是固定流程、无工具无循环，故障只可能落在"检索没召回"和"提示有问题"两类——这本身是结构性差异。

| 案例 | trace 证据 | 归类 | 根因 | 改法 |
|---|---|---|---|---|
| **id=4** 考勤打卡<br>答出钉钉/两次/上下班，缺工作时间 | 三块中均无"9:00至12:00" | ①检索没召回 | 500字硬切，块0、块2 各横跨三章，考勤条款被稀释，工作时间切到了没进 Top-3 的块里（第11周"万能块现象"同源） | 按章节标题切 |
| **id=2** 薪酬结构<br>答出四部分，漏发薪日 | 块0 中四部分与"每月15日"都在 | ②提示有问题 | 提示只说"根据资料回答"，没要求把相关信息答完整 | 加"完整列出"要求 |
| **id=6** AI工具<br>直接拒答 | 块0、块1 全来自AI趋势文档，块2 是考勤薪酬；员工手册第六章一段没捞到 | ①检索没召回 | 语义漂移——"AI工具"把检索带向技术文档占掉两坑；Top-K 硬指令必凑三条。手写版无元数据，无法 filter | 加 source 元数据 + 过滤 |
| **id=7** 入职半年<br>引用了"满一年"却说找不到 | 块0 含"员工连续工作满一年后享受带薪年假"，模型原样引用 | ②提示有问题 | `build_prompt` 里"资料不足就说未找到"是第11周为防幻觉写的，导致只要没有字面答案就拒答。**防幻觉防过头，把推理一起防掉** | 改为"可基于资料推理并说明依据" |

## 五、改进方向（按优先级）

1. **【最该先动】改提示词，两处一起改**：①拒答指令改成"允许基于资料推理"；②加上"把资料中与问题直接相关的信息完整列出"。两句话治两个病——①对应 id=7，②对应 id=2。成本最低，各带回一题。
2. **改分块策略，按章节标题切而非 500 字硬切**：影响 id=4、id=6 和第 11 周记录的"万能块"。影响面最大，但改动量大、需重建索引。
3. **给手写版加 source 元数据 + 过滤**：针对 id=6 的跨文档串味。依赖第 2 项——要先有按文档切块的干净结构。
4. **扩充评测集的多轮题**：id=5 暴露了小知识库上多轮题区分度不足。需加入"必须依赖前文才能答对"的题（如前文给别名、后文用别名追问）。

## 六、结论

### 手写 vs 框架

1. **框架版提示词更松**（没有"不足以回答就拒答"的硬指令），所以敢推理（id=7）、敢答完整（id=2）。这一条改手写版的提示词就能追上。
2. **框架版检索质量更高**（id=4、6 手写版都没召回该召回的块）。但两版索引来源不同（JSON vs Chroma），此项归因**未经验证**，待查。
3. **框架版有记忆、有工具自主决策，但这次评测集没测出这两项优势**——id=5 手写版无记忆也答对了。

**一句话**：这次对比的结论不是"框架比手写强"，而是"框架帮你省下的那部分代码，恰好是检索质量、记忆、可观测性这些容易出问题的地方"。手写版要追上框架版，得自己补的正是这三块——补完之后，其实你也就是把框架又写了一遍。

### 当前水平与短板

框架版 llm_judge 0.90（9/10），但这个数偏乐观：id=5 手写版无记忆也答对，说明它测不出记忆能力，这一分含水分；id=10 两版都错、未追因。扣掉存疑的题后真实区分能力低于 0.90，具体多少这套评测集给不出答案——这正是改进方向第 4 条要解决的。

**已知短板**只有 id=10（待追因）。**未知短板**是记忆和工具自主决策这两项原生能力，评测集根本没给它们出过题，要等第 22 周扩充评测集后才知道值多少分。

### 什么时候手写，什么时候上框架

- **手写适合**：流程固定、知识库小（十几块）、不需要多轮记忆、追求低延迟（0.65s vs 2.04s）。比如内部小工具、一次性问答脚本。
- **框架适合**：需要多轮记忆、需要模型自主决策（该不该检索、检哪份文档）、需要可观测性和成本核算、知识库会持续增长。

框架的价值不在"更聪明"，在"少写代码 + 自带可观测性 + 可扩展"。
