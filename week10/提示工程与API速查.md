## 一、提示的四要素

**角色 / 任务 / 约束 / 格式** —— 写提示时逐个自问：

| 要素 | 自问 | 例子 |
|---|---|---|
| 角色 | 让它以什么身份回答？ | 「你是一个信息提取器」 |
| 任务 | 具体要它干什么？ | 「从句子里提取姓名、年龄、城市」 |
| 约束 | 有什么不许做？ | 「不要解释、不要代码块」 |
| 格式 | 输出长什么样？ | `{"name": "...", "age": 数字}` |

⭐ 四要素里最容易漏的是**约束**——不写"不许做什么"，模型就会自由发挥。

## 二、三种提示策略

| 策略 | 一句话 | 最适合 | 代价 |
|---|---|---|---|
| Zero-shot | 只描述、不给例子 | 简单、常见的任务 | 格式不可控 |
| Few-shot | 给几个示范让它照做 | 格式要求严、标准微妙的任务 | 例子给得差，输出就跟着差 |
| CoT | 让它一步步想 | 需要多步推理、分析、规划 | ⭐ 输出**变长**、token 变多、更慢更贵 |

⭐ **纠错记录**：我一度以为 CoT"回复比较精炼"——**错了，正好相反**。CoT 是用更长的输出、更高的成本，去换准确率。

**我的决策原则**（接周三评测表的结论）：
- 简单任务 → Zero-shot，够用就别加钱。
- 要锁死格式/标准 → Few-shot。
- 要推理、要正确率 → CoT，且接受它更贵更慢。
- 选之前先跑评测表：准确性 / **稳定性（同一提示跑 3 次看一致性）** / 成本 / 适用场景。

## 三、API 调用模板（五环）

```
调 API → 解析 JSON → Pydantic 校验 → 异常处理/重试 → 返回结构化对象
```

设计三问（动手前先想）：
1. **输入**：提示内容，可选 system / temperature / model
2. **输出**：⭐ 返回**校验过的 Pydantic 对象**，不是原始字符串、也不只是 dict
3. **流程**：六步搭 —— 骨架 → 加 `json.loads` → 加 `model_validate` → 加 try-except → 加重试循环 → 压力测试

异常要**分类接**，不能一个 `except` 兜底：

| 异常 | 什么情况 | 该怎么办 |
|---|---|---|
| 网络/超时 | 网抖了 | 重试有用 |
| `json.JSONDecodeError` | 返回的不是合法 JSON | 重试有用（+反馈"上次格式不对"） |
| `ValidationError` | JSON 合法但字段/类型不对 | 重试**可能**没用 |

重试：最多 3 次，每次失败先记录再来一轮，全失败**优雅返回 None**，不许让程序崩。

⭐ **压力测试学到的**：确定性失败（句子里压根没这个字段、数值超出校验范围）**重试救不回来**——重试只能救随机性失败。

## 四、常用参数

**`temperature`：调的是候选词概率表的陡峭程度。**
- 模型每吐一个字，都在算一张候选词概率表（"今天天气很" → 好 60% / 热 25% / 差 10%）
- 调高 → 表变平 → 冷门词也可能被抽中 → 发散、有创意
- 调到 0 → 永远挑概率最高的那个 → 同输入同输出
- **要 JSON、要分类、要提取 → 一律设 0**
- ⚠️ 实测：temperature=0 **不保证 100% 一模一样**；它在"答案空间小"的任务上效果最明显

**`max_tokens`：输出长度的硬闸刀。**
- 设太小 → JSON 被从中间**砍断** → `json.loads()` 直接报错
- 设太大不浪费（它只是上限，不够长不会硬凑）→ **宁可给宽松点**

**`system`：最高指令，相当于公司规章制度。**
- system = 长期规章，user = 这次的具体任务
- 「只输出 JSON、别啰嗦」这类规矩，放 system 比放 user 管用

## 五、稳定输出 JSON 三招

> ⭐ **重要区分**（我自测时答错的地方）：这三招全在**"下单侧"——写在提示里**，一行 Python 都没有。
> 第三节那个五环是**"收货侧"——代码兜底**。两套手段，别混成一套。

1. **在 user 里画出 JSON 的确切形状**（键名、结构直接示范给它看，本质是 Few-shot）
2. ⭐ **逐字段说明：名称、类型、取不到值时怎么办**
   —— 「name 是字符串，age 是整数，没提到年龄就填 null，不要编」
3. **在 system 里立规矩**：「只输出 JSON 本身，不要任何解释，不要用 ```json 代码块包裹」

外加参数侧一招：**temperature = 0**。

公式：**低温 + system 立规矩 + 明确格式/禁啰嗦 = 稳定 JSON**

⚠️ **模型爱加的两种废话** → 怎么治：

| 废话 | 长什么样 | 治法 |
|---|---|---|
| 开场白 | "好的，这是提取结果：" | 提示里禁止 + 拿到后 `.strip()` |
| 代码块围栏 | ` ```json ... ``` ` | 提示里禁止 + `.replace("```json","").replace("```","")` |

两者都会让 `json.loads()` 挂掉——**提示里堵一遍，代码里再洗一遍，双保险**。

⭐ 补充：很多平台支持 `response_format={"type":"json_object"}`，能强制输出合法 JSON，支持就用上。

## 六、🔴 安全铁律

**Key 泄露 = 别人能用我的身份、花我的钱、访问我的数据。**

- **怎么存**：写进 `.env`，代码里用 `os.getenv()` 读，**绝不硬编码进 .py**
- **怎么防泄露**：`.gitignore` 里加一行 `.env`
- **push 前查什么**：`git status` —— **确认 `.env` 不在待提交列表里**，看不到才 push
- 🔴 **最狠的一条**：Key 一旦推上过 GitHub，**删掉文件再 push 一次也没用**——`git log` 里历史还在，谁都能翻出来。
  **唯一解法：去平台把那把 Key 作废，重新生成一把。**

> 这条和第三周的 GitHub Token 是同一套工具、同一条戒律。

## 附：一句话记忆

- 模型的输出是**不可信的外部数据**，Pydantic 就是给它装的**安检门**——`json.loads` 只查语法合法，安检门查的是**字段、类型、空值**。
- 提示工程解决"让它少犯错"，代码兜底解决"它犯错了我不崩"。**两个都要有。**
